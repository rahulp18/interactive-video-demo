# Decisions log

Append-only, newest at bottom. Only decisions with a non-obvious WHY. Format:
`## YYYY-MM-DD — Title` / Decision / Why / Consequences.

## 2026-11-03 — Monorepo with pnpm + Turborepo
Decision: `apps/web`, `apps/mobile`, `packages/shared`.
Why: web and mobile share types/logic and one backend.
Consequences: shared package ships raw TS (no build); consumers must transpile it.

## 2026-11-03 — Single Session table for web cookies and mobile bearer tokens
Decision: store only SHA-256 of the token in `Session.tokenHash`.
Why: one auth mechanism for both clients; DB leak doesn't expose usable tokens.
Consequences: tokens can't be recovered; revocation = delete row.

## 2026-11-03 — Integrity rules live in Postgres
Decision: CHECK constraints and composite FKs (e.g. response's selected option must belong to its interaction).
Why: guarantees hold regardless of which client/code path writes.
Consequences: schema changes need migrations; app code should surface constraint errors gracefully.

## 2026-11-03 — Web auth UI: server-rendered pages, session read on the server, shadcn/ui
Decision: pages are server components; only forms (`components/auth/*Form.tsx`) and `LogoutButton` are client. Protected/guest gating reads the HttpOnly cookie on the server (`lib/auth/server.ts` → `validateSession`) inside `<Suspense>` (required by `cacheComponents`). No client-side auth context. UI uses shadcn/ui (`base-nova`, neutral) in `components/ui/`.
Why: no auth flash, no tokens in JS, and calling our own `/api/auth/me` over HTTP from a server component is wasteful. Do NOT cache the user (`use cache: private`): logout/revocation must apply immediately.
Consequences: `/api/auth/register` now also signs the user in (cookie for web, raw token for mobile, same as login). Session is an opaque revocable token, not a JWT. shadcn CLI generated a bogus `cn` npm dep/import; replaced with clsx + tailwind-merge in `lib/utils.ts`. Vitest inlines `next` so `vi.mock("next/server")` works.

## 2026-11-03 � Video upload via UploadThing, persisted in `onUploadComplete`
Decision: single `videoUploader` file route (`app/api/uploadthing/core.ts`): auth in `middleware` via the existing `requireUser`/`assertSameOrigin` (cookie or bearer), video-only, 512MB, 1 file, mp4/webm/mov. The Video row is created only in `onUploadComplete`, idempotent on unique `Video.fileKey`; uploader id comes from middleware metadata. If the DB write fails the UploadThing file is deleted (UTApi). Stored URL is `file.ufsUrl` (`url`/`appUrl` are deprecated).
Why: UploadThing calls `onUploadComplete` via a signed callback, possibly more than once; the unique key makes retries safe and no row exists for failed uploads. Added `Video.uploaderId/fileKey/originalName/sizeBytes` (migration `add_video_upload_fields`).
Consequences: `Video.duration` is browser-reported (UploadThing doesn't probe media) � treat as a hint; no server-side ffprobe yet. Files are public-read URLs. When planning migrations the `db` ref was stale (pointed at init) so `migration plan` needed `--from <head hash>`.

## 2026-11-03 - Interaction updates preserve option rows; timestamps validated against Video.duration
Decision: `PUT .../interactions/[id]` matches options by `id` (update in place), creates new ones and deletes omitted ones in one transaction; kept options are first parked at `position + 1_000_000` because `(interactionId, position)` is unique and not deferrable. Timestamps are rounded to 0.1s and must be within `0..Video.duration`.
Why: `InteractionResponse` has a composite FK to options with NoAction, so delete-and-recreate would break (or destroy) existing responses; removing an option that already has responses returns 409 instead of partially applying.
Consequences: Duration is the browser-reported hint (see upload decision), so a wrong duration also constrains where interactions can be placed. Inside `db.transaction` only `create`/`createAll`/`updateAll`/`deleteAll` are used (single-row `update`/`delete` and nested creates hang inside a tx).

## 2026-11-03 - `getCurrentUser` calls `connection()`
Decision: `lib/auth/server.ts` awaits `connection()` before reading the cookie.
Why: `validateSession` compares against `new Date()`, which Next 16 reports as an error during the runtime prerender used by partial prefetching (it was logged for /dashboard and would be for every protected page).
Consequences: the user/session is never part of a prerendered or prefetched shell, matching the earlier "do not cache the user" rule.

## 2026-11-03 - Upload takes an optional title
Decision: `videoUploadInput` accepts `{ duration, title? }`; `saveUploadedVideo(userId, duration, file, title?)` falls back to the filename. The /upload page requires a title before the file picker is enabled.
Why: users name the video up front; no second upload mechanism or rename-after-upload step needed.

## 2026-11-03 - Public watch links are unlisted tokens; anonymous answers are not persisted
Decision: sharing = nullable unique `Video.shareId` (migration `add_video_share_id`). Correctness is never sent to the browser; quizzes are graded by a public endpoint after the viewer answers. No response rows are written for anonymous viewers.
Why: `InteractionResponse` is keyed by (userId, interactionId) with a CHECK/composite FK, so anonymous storage would need a schema redesign (anonymous viewer identity) - deferred until analytics is in scope.
Consequences: revoking sets shareId to null (old links die at once; re-enabling issues a new token). The in-memory rate limiter is per instance; put a shared limiter in front for multi-instance deployments.

## 2026-11-03 - Identified responses, Library, and text answers
Decision: (1) viewers answer as signed-in users so owners can see who responded (`InteractionResponse` stores the first answer per user+interaction); anonymous link visitors can answer but nothing is stored, and the watch page says so. (2) `Video.isListed` adds a platform Library alongside the secret link; listing requires a link and unsharing clears it. (3) `Interaction.answerType` CHOICE|TEXT; typed answers go in `InteractionResponse.textAnswer`, with CHECKs `isSkipped = (no option and no text)` and "never both". (4) Login/register honour `?next=` only for same-site absolute paths.
Why: the owner needs per-person results; the existing table already modelled one response per user; typed answers avoid forcing everything into options.
Consequences: owners can see viewers' names and emails (the watch page discloses this). `?next=` is read via `useSyncExternalStore`, not `useSearchParams()`, because the auth forms sit in a prerendered shell with no Suspense boundary. Changing a question from CHOICE to TEXT deletes its options and fails with 409 if any option already has responses.

## 2026-11-10 - Answering requires sign-in; re-answering replaces the earlier answer
Decision: `checkPublicAnswer` throws UNAUTHENTICATED (401) for anonymous viewers. A signed-in viewer may answer the same interaction again (e.g. after a refresh or "Watch again"); the single `InteractionResponse` row (unique per user+interaction) is updated, so the latest answer stands. The watch page no longer pre-marks answered questions as done. The player shows a sign-in/register prompt to anonymous viewers. Supersedes "anonymous answers are graded but not stored" and "first answer wins".
Why: anonymous answers can't be tied to anyone (no identity), so only signed-in answers are recorded; the product wants viewers to be able to redo questions, and the one-row-per-user schema keeps owner results unambiguous.
Consequences: owners see only each viewer's latest answer (no attempt history; add an attempts table if that is ever needed). Mobile clients get 401 for anonymous answers.

## 2026-11-20 - Explicit STUDENT/TEACHER roles; existing users became TEACHER
Decision: `User.role` enum, default STUDENT, added by migration `20261120T0805_add_user_role` whose data transform sets every pre-existing user to TEACHER. Public registration cannot choose a role. Authorization is centralized in `lib/auth/roles.ts` and enforced on the server (page guards + API `role` option), not only by hiding nav links.
Why: before roles every account used the teacher UI, so existing accounts must keep working; a student must never reach teacher pages/APIs or upload; `?next=` must not become a way to cross roles.
Consequences: there is no way to create a teacher in the UI (promote with SQL `UPDATE "User" SET role='TEACHER'`). Tests that create owners directly in the DB must pass `role: "TEACHER"`. Teacher pages still render their static header (outside Suspense) before the redirect fires, but no data is fetched or sent.

## 2026-11-20 - PARICHAY Phase 1: virtue data model and rule-based scoring/SWOT engine
Decision: (1) Raw module score per virtue is MIN-MAX scaled, (earned - min) / (max - min) * 100 over answered interactions whose options weigh that virtue (an option with no weight row counts 0). The SRS's literal "earned / max" breaks with negative weights (a neutral answer would equal a harmful one); min-max puts neutral at 50. A virtue no answered interaction weighs, or with no spread between best and worst, gets NO score for that module (not 0). (2) A module counts only once `ModuleProgress.completedAt` is set, and its scores are timestamped with it (seeds may backdate it). (3) Running child score = exponentially recency-weighted average over modules (newest weight 1, decay 0.8 per older module). Composite = 60% child / 25% parent / 15% teacher; parent/teacher 1-5 ratings map linearly to 0-100 and the LATEST rating per kind counts; a missing source is dropped and the blend re-normalised over the sources present. (4) Defaults (all in `SCORING_RULES_V1`): confidence by scored interactions <8 insufficient, 8-14 low, 15-29 medium, >=30 high (insufficient virtues are left out of the SWOT); trend = running score now minus as of 90 days ago (>=+5 rising, <=-5 falling, else stable; no data point that old = stable, delta null); Strength composite>=70 and trend not falling; Weakness composite<45 OR parent marked IMPROVE and child score<60; Opportunity composite 45-70 and rising; Threat = fell >=15 over the 90-day window OR |parent - child| >=30 (admin flag skipped); up to 3 evidence responses per item (strongest examples first). (5) Parents/teachers have no accounts, so `VirtueRating` stores raterKind + free-text raterName, NOT a user FK; the 1-5 range is a DB CHECK, the max-3 strengths / max-3 improve rule is app-level (`validateParentMarks`). (6) `buildChildView` returns a type with no score/percentage/weakness/threat field (only superpowers, badges, whole-number star and module counts), so it cannot leak numbers by construction.
Why: scoring must be explainable and traceable (every result carries `ruleVersion`); child-facing output must be encouraging only (FR-6.15).
Consequences: changing a rule = a new rules object, never editing V1 in place. The engine (`lib/scoring/`) is pure so it can move to an async worker unchanged; only `lib/scoring/service.ts` touches the DB and computes on read (no caching of child data). Other modeling: Module is 1:1 with Video (plain videos are untouched); secondary virtues live in `ModuleSecondaryVirtue` (position 1|2 unique per module, a mirrored `primaryVirtueId` with a cascading composite FK + CHECK stops the primary being a secondary); `Interaction.presentationStyle` is display-only (default MORAL_CHOICE); `InteractionResponse` gained responseTimeMs/replayCount/attemptCount (the answer endpoint leaves defaults until Phase 4, attemptCount should increment on re-answer). The 10 virtues are inserted by the migration's data transform (reference data, not demo data).

## 2026-11-20 - PARICHAY Phase 2: demo content, designed profile, reset instead of re-seed
Decision: (1) PLACEHOLDER CLIPS, ORIGINAL SCRIPTS. Real story videos do not exist yet, so every demo module plays "Big Buck Bunny" (CC BY 3.0, Blender Foundation; archive.org mp4 and Wikimedia webm). The stories, questions and weights are original and are the real deliverable. All clip facts (url, mime, duration, size, licence, attribution) live in ONE manifest, `scripts/demo/content/clips.ts`; question times are stored as fractions of the clip duration, so swapping in a real video = edit one manifest entry and re-run `seed:demo`. The credit line must be shown wherever the demo videos are shown. (2) DESIGNED PROFILE. The demo student's history is not random: each answer is a chosen option (`content/history.ts`, picks per module) so that `SCORING_RULES_V1` yields every SWOT quadrant and confidence band (Compassion high/strength, Friendship medium/strength, Self-Discipline weakness by score, Honesty weakness by parent mark, Perseverance opportunity, Responsibility decline threat, Work parent-gap threat, Faith insufficient). It was planned backwards from the rules: 5 questions per module, up to 3 virtues weighed per question, so the scored-answer counts land exactly on 30 / 15 / 8 (high / medium / low) and Faith stays at 3; picks were tuned offline with the real engine (`scripts/demo/profile.ts`). The rules and engine were NOT changed to fit. `tests/demo-seed.test.ts` asserts the whole profile (offline and through the DB service), so editing a weight, pick, date or rating that breaks the profile fails a test. (3) RESET, NOT A FRESH SEED. All history dates are relative to "now" (modules completed 14..118 days ago, ratings 6/12/95 days ago), so the 90-day trend window drifts as time passes and a rehearsal leaves answers behind. `pnpm --filter web demo:reset --yes` deletes the demo student's progress, responses and ratings and re-creates the designed history relative to today; content and all other users are untouched. Run it before every demo. `seed:demo` only writes the history when the student has none, so it stays idempotent.
Why: a believable demo needs a student whose results tell a story on every screen; relative dates keep the trend rule meaningful; resetting one user is fast and safe on a public deployment, while re-seeding content would churn ids.
Consequences: demo rows are recognised ONLY by natural keys: `Video.fileKey = "demo:<slug>"` (never an UploadThing key: nothing deletes demo videos remotely), demo emails on the reserved `@demo.parichay.test` domain, journey titles; per-user deletes first check the user is on that domain. Both scripts print the DB host only, need `--yes`, and honour `DEMO_ALLOWED_HOST` as a pin to the intended (dev) database; passwords come from `DEMO_PASSWORD` and are set only when an account is created (`--set-password` to change). Demo videos get a derived stable `shareId` (public, unlisted). Scripts run through `tsx --conditions=react-server` (tsx added as a dev dependency) so they can reuse `server-only` services. Open for the live demo: Courage "Brave Little Parrot" not started (Perseverance Path level 2, unlocked), Faith "Little Mango Seed" in progress (2 answers saved).


## 2026-11-20 - PARICHAY Phase 3: student shell, username + PIN login with a database lockout
Decision: (1) LOCKOUT IN THE DB. A 4-digit PIN has 10,000 values, so each account locks for 15 minutes after 5 wrong PINs, stored in `User.pinFailedAttempts` / `pinLockedUntil`; the counter is incremented with compare-and-set (`updateAndCount` on the old value) so parallel guesses are each counted, and a correct PIN is re-checked against the lock after hashing. The in-memory per-IP `rateLimit` is also on the route but is only a second layer. (2) SERVER-SIDE CREDENTIALS ONLY. Usernames and PINs are set by `setStudentCredentials` (seed, tests), never by a UI or the child: real child accounts belong to a parent (FR-4.1-4.3) and there are no parent accounts in the demo. Unknown username, wrong PIN, no PIN and teacher accounts all get the same 401 (with a dummy hash for similar timing); only a locked account gets a distinct message (it reveals the account exists, which the spec accepts). Teachers can never have a PIN (DB CHECK). (3) THEME BY ATTRIBUTE. The kid-friendly look lives under `[data-audience="student"]`, set by `AppFrame` for students only, so teacher pages keep the neutral tokens untouched and no teacher component needed changes; light/dark and the 48px touch-target rule are tokens/CSS in that scope. (4) STUDENT HOME IS `/student`; `/library` became a shared route with no student-menu entry, so `intendedRoleFor` no longer treats it as a student signal; `/home`, `/results` and four placeholder pages were deleted (old URLs 404).
Why: serverless instances do not share memory, so only the database can enforce a per-account limit; an attribute scope is the least invasive way to restyle one audience; child-facing screens need big targets and warm, simple visuals (SRS section 3, NFR-9.19/9.20).
Consequences: `demo:reset` clears lockouts for demo students (so a rehearsal cannot lock the presenter out) but never touches usernames or PINs; `seed:demo` needs `DEMO_STUDENT_PIN` (4 digits). The PIN login adds the `PIN_LOCKED` (429) auth error code. Phase 6 decides whether `/student/parent` needs a parental gate.
