## Auth design (from schema)
- One `Session` table serves both clients: web uses a cookie, mobile a bearer token. Only the SHA-256 of the token is stored; passwords are hashed in application code.

## Roles (STUDENT / TEACHER)
- `User.role` (enum `UserRole`, default STUDENT). Rules live in ONE pure module, `lib/auth/roles.ts`: `homePathFor` (STUDENT `/student`, TEACHER `/dashboard`), `TEACHER_ONLY` / `STUDENT_ONLY` path prefixes, `canAccessPath`, `postAuthPath(role, next)` (validated `next` only if the role may open it, else home; decodes the path so `/%64ashboard` can't bypass). Shared routes: `/library`, `/settings`, `/watch/*`, auth pages. `intendedRoleFor` (display only) no longer treats `/library` as a student signal.
- Server enforcement: pages call `requireTeacher()` / `requireStudent()` (`lib/auth/server.ts`, wrong role -> redirect to own home; every teacher page must call it itself); APIs use `handle(request, fn, { role: "TEACHER" })` or `requireRole(request, role)` (`lib/auth/request.ts`) -> 403 `FORBIDDEN`; UploadThing middleware requires TEACHER. New teacher-only page/route = add the guard AND the prefix in `roles.ts`. `/api/public/*` (answer) and `/library` stay role-agnostic.
- `redirectIfAuthenticated(next)` and the forms' `succeed(role)` both use `postAuthPath`. `AppFrame` takes `user.role` and picks `navItemsFor(role)`.
- Public registration always creates STUDENT (role set in `registerUser`, never read from the body). Teachers are granted out of band (SQL/admin), there is no UI for it yet.

## Sign-in / sign-up UI and first-time welcome (2026-11-20)
- `/login` and `/register` share `components/auth/auth-card.tsx` (`AuthCard`: brand panel + form on lg, compact header below; theme tokens only, no brand colours) and `useAuthForm` (loading lock, `succeeded`, deferred focus). `TextField` inputs are 44px on mobile. Do NOT add remember-me / forgot-password / demo-login UI or pre-filled credentials: none of those exist server-side (fixed 7-day session cookie, no reset flow, no demo account).
- Student PIN sign-in (Phase 3, FR-4.4): `/login` offers "I'm a student" (`StudentLoginForm`: username + `PinPad`, auto-submit on the 4th digit) and "Grown-up / Teacher" (`LoginForm`, unchanged), via `components/auth/SignIn.tsx` (defaults to student unless `?next=` is a teacher route). Endpoint `POST /api/auth/pin-login` (`lib/auth/pin.ts#loginWithPin`): same-origin check, per-IP `rateLimit`, cookie for web / token for mobile. `User.username` (unique, lowercase, DB CHECK `^[a-z0-9_]{3,20}$`), `pinHash` (scrypt, same hasher as passwords; CHECKs: students only, needs a username), `pinFailedAttempts` / `pinLockedUntil`. 5 wrong PINs lock the account for 15 minutes (state in Postgres, compare-and-set counter); unknown user / wrong PIN / no PIN / teacher all return the same generic 401, a locked account returns 429 `PIN_LOCKED` with a child-friendly message. PINs are set only server-side (`setStudentCredentials`), never through the UI; registration is unchanged.
- Student theme: `AppFrame` sets `data-audience="student"` on its root for students only; tokens (warm primary, larger radius, 17px base, Nunito via `next/font` with `preload: false`) are defined under `[data-audience="student"]` and `.dark [data-audience="student"]` in `globals.css`, plus a CSS rule giving every button/input in that scope a 48px minimum. Teacher pages never get the attribute and render as before. `student/layout.tsx` sets `viewportFit: "cover"` for safe-area padding on student pages only.
- Right after public registration the client goes to `/welcome` (`welcomePathFor` in `roles.ts`, student-only, `?next=` preserved): a 2-step explainer in `components/onboarding/WelcomeSteps.tsx`. It collects and stores NOTHING (the User row has no profile fields beyond name/email). If onboarding state or preferences are ever needed, that requires a schema change (e.g. `User.onboardedAt`) plus an endpoint; none exists.

## Web app structure (verified 2026-11-03)
- Authenticated pages live in route group `app/(app)/` (URLs: /dashboard /upload /videos /videos/[id] /surveys /quizzes /settings). `(app)/layout.tsx` wraps `AppShell` (session check + sidebar/top bar, `components/layout/`) in Suspense; each page ALSO calls `requireCurrentUser()` itself because layouts don't re-run on client navigation.
- Pages are server components that call services directly (`lib/videos/service.ts`, `lib/interactions/service.ts`); browser code calls the REST routes via `lib/videos/client.ts`. Pages read `params`/`searchParams` in an inner async component under `<Suspense>` (cacheComponents).
- API (all cookie-or-bearer authed via `lib/api/route.ts#handle`, errors use the auth error envelope): `GET /api/videos`, `GET|PATCH|DELETE /api/videos/[id]`, `POST /api/videos/[id]/interactions`, `PUT|DELETE /api/videos/[id]/interactions/[interactionId]`, `GET /api/interactions?type&q&videoId` (grouped by video). Ownership = query by `{ id, uploaderId }`, then `{ id, videoId }`; foreign/missing both give 404.
- Shared interaction rules (types, timestamp parse/format, `validateInteraction`) are in `lib/interactions/model.ts` and used by both server and editor form.
- Public viewing: `Video.shareId` (null = private, 16-char random token; clearing revokes). Owner toggles via `PUT|DELETE /api/videos/[id]/share` (`SharePanel` in the editor). `/watch/[shareId]` (outside `(app)`, no auth, noindex) renders `InteractivePlayer`; `lib/watch/service.ts` returns interactions WITHOUT `isCorrect`, and `POST /api/public/videos/[shareId]/interactions/[id]/answer` grades quizzes server-side (rate-limited in memory, same-origin checked). Only signed-in viewers can answer (anonymous get 401); one `InteractionResponse` per user+interaction, and answering again replaces it (latest wins). `Video.isListed` puts a shared video in the `/library` tab (author name shown). Owners see who answered what at `/responses` and `/responses/[videoId]` (+ CSV at `GET /api/videos/[id]/responses?format=csv`). Questions have `answerType` CHOICE (options) or TEXT (typed; TEXT quizzes use `Interaction.correctAnswer`, compared via `normalizeAnswer`). Auth pages honour a safe `?next=` (`lib/auth/redirect.ts`).
- Surveys/Quizzes pages are read-only views over `Interaction` (no template models); creating/editing happens in the video editor via `?new=SURVEY|QUIZ` / `?edit=<id>` deep links.

## PARICHAY data model and scoring engine (Phase 1, 2026-11-20)
- New tables: `Virtue` (10 reference rows seeded by migration `20261120T0904_add_parichay_virtue_model`), `Module` (1:1 with `Video`, optional), `ModuleSecondaryVirtue` (max 2, never the primary), `Journey`, `JourneyModule` (level >= 1 + position), `OptionVirtueWeight` (-2..+2, non-zero, unique per option+virtue), `ModuleProgress` (per user+module; `completedAt` is what makes a module count), `VirtueRating` (parent/teacher 1-5 per virtue, rater is a name, not a user). `Interaction.presentationStyle` (display only) and `InteractionResponse.responseTimeMs/replayCount/attemptCount` were added. Videos without a Module behave as before.
- Engine: `apps/web/lib/scoring/` — `rules.ts` (`SCORING_RULES_V1`, versioned), `types.ts`, `engine.ts` (pure: `scoreModule`, `buildAssessment`, `buildChildView`, `blendComposite`, `validateParentMarks`...), `index.ts` barrel, `service.ts` (server-only DB loader: `loadAssessmentInput`, `getAssessment`, `getChildView`; compute on read). Tests: `tests/scoring.test.ts` (pure), `tests/scoring-schema.test.ts` (DB constraints + virtue seed). Rationale and defaults: decisions.md 2026-11-20.

## PARICHAY demo content and scripts (Phase 2, 2026-11-20)
- Content (plain typed data, readable without code): `apps/web/scripts/demo/content/` - one file per journey (`perseverance-path.ts`, `honesty-trail.ts`, `kindness-and-friends.ts`), `journeys.ts`, `clips.ts` (placeholder-video manifest + licences), `accounts.ts`, `history.ts` (the demo student's designed history: picks, dates, ratings), `index.ts`. 10 modules (one per virtue), 5 questions each, 3 journeys x 2 levels.
- Logic: `scripts/demo/seed-lib.ts` (idempotent, diff-based; no argv/exit so tests call it), `profile.ts` (content+history -> engine input with NO database; used to tune/test), `guard.ts` (host print, `--yes`, `DEMO_ALLOWED_HOST`), CLIs `seed.ts` / `reset.ts`. Tests: `tests/demo-seed.test.ts`.
- Commands: `pnpm --filter web seed:demo --yes` (create/update content, accounts, journeys; history only if the student has none) and `pnpm --filter web demo:reset --yes` (**run before every demo**: re-creates the demo student's progress/responses/ratings relative to today). Env: `DEMO_PASSWORD` (required), `DEMO_ALLOWED_HOST` (optional pin); see `.env.example`.
- Natural keys: `Video.fileKey = "demo:<module-slug>"`, demo emails `content@ / aarav@ / meera@demo.parichay.test` (reserved `.test` domain; per-user deletes check it), journey titles. Demo videos have a derived `shareId` and `isListed = false`; they are NOT UploadThing files. Accounts: content team (TEACHER, owns the videos), Aarav (demo student with history), Meera (fresh student). Accounts also carry a student `username` (`aarav`, `meera`); `seed:demo` sets the shared PIN from `DEMO_STUDENT_PIN` (idempotent, never printed) and `demo:reset` clears lockouts but keeps credentials.
